# 채팅 화면 렌더링 성능 (#14 완료 기준)

1만 토큰 응답을 스트리밍으로 그리는 동안 긴 작업(50 ms 초과)이 몇 번 생기는지 잰 기록이다.

- 환경: macOS, Node v22.22.0, Playwright 1.65.0 Desktop Chrome(headless), 프로덕션 빌드, `FAKE_RUNTIME=1`
- 코드: `feat/chat` 브랜치 (#14), 기준 커밋 `2480224` 위 작업
- 자동 테스트: `e2e/chat.spec.ts` › "a 10,000-token reply streams without long main-thread tasks"
- 절차: 마크다운 청크를 먼저 불러온 뒤(`/md`), `/burst 10000`(1만 단어, 60단어마다 굵은 글씨 + 문단 나눔, 20토큰마다 1 ms 쉼)을 보내고 `PerformanceObserver("longtask")`로 끝날 때까지 기록

| 절차 | 결과 | 관측 | 증거 |
|---|---|---|---|
| 1만 토큰 스트리밍 (1회차) | 통과 | 스트리밍 1,319 ms · 긴 작업 0회 · 최대 0 ms | `[perf]` 테스트 출력 |
| 1만 토큰 스트리밍 (2회차, 전체 E2E 병렬 실행 중) | 통과 | 스트리밍 1,830 ms · 긴 작업 0회 · 최대 0 ms | `[perf]` 테스트 출력 |
| 리뷰 1차 반영 후 (단독) | 통과 | 스트리밍 1,312 ms · 긴 작업 0회 · DOM 갱신 80회(≈ 프레임 수) | `[perf]` 테스트 출력 |
| 리뷰 1차 반영 후 (전체 E2E 병렬) | 통과 | 스트리밍 1,834 ms · 긴 작업 0회 · DOM 갱신 90회 | `[perf]` 테스트 출력 |
| 대조: 프레임 묶음 제거(이벤트마다 반영) | 실패(의도) | DOM 갱신 505회 — 테스트 상한(초당 60프레임 × 1.5 + 20) 초과로 검출 | 뮤테이션 확인 |

판정: 통과 (목표: 50 ms 초과 0회) · 판정자: Review & Test agent 확인 필요 · 커밋: #14 PR 머지 커밋

렌더링 방식: 이벤트를 애니메이션 프레임마다 한 번에 반영하고(토큰마다 다시 그리지 않음), 답을 빈 줄 기준 블록으로 나눠
블록별로 메모이즈해 스트리밍 중에는 마지막 블록만 다시 파싱한다. 끝난 뒤에도 같은 컴포넌트 트리를 유지해 전체를 다시 그리지 않는다.
CI에서는 느린 머신을 고려해 3회까지 허용하고 수치를 기록한다.
