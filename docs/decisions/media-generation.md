# 결정 기록 — 미디어 생성 (OpenRouter 이미지·음성·음악·영상, #238)

- 날짜: 2026-11-24
- 작성: Dev agent (Claude Opus 5.5), 계획: #238 본문, 사용자 결정(2026-11-24 댓글)
- 관련: `docs/ops.md` 51절(운영)·46절(음성 전사 외부 대체), `apps/server/src/media/`
- 범위: **1단계** — 관리자 설정과 공통 기반. **2단계** — 이미지·음성 동기 도구와 채팅 재생(§6–§8). **3단계** — 영상 확인 카드·비동기 작업·카드 안 재생기(§14). 음악(Lyria)은 3단계에서 빠져 별도 이슈.

## 1. 설정 모양
- 한 JSON 행(`settings.media.settings`, `MediaSettings` — `packages/shared/src/media.ts`): `kinds.{image,speech,music,video}.{enabled, model}`, `dailyCostLimitUsd`, `perRunLimits.{종류}`, `videoDefaultSec`. 2·3단계 도구는 `app.media.settings.get()`으로 읽는다. 종류를 하나 더하려면 `MEDIA_KINDS`·카탈로그 URL·기본값에 넣는다.
- 기본값: 모두 꺼짐·모델 없음(호출마다 비용), 하루 $50(사용자 결정), 실행당 이미지 4·음성 3·음악 1·영상 1(이슈), 영상 8초(사용자 결정). 음악은 처음부터 다른 종류와 같은 자리에 둔다(사용자 결정 "기본 포함") — 호출 방식은 3단계에서 가짜 서버로 먼저 확인한다.
- 켜려면 모델이 있어야 한다(형식 검사). 새로 켜거나 새 모델을 고르면(꺼진 종류도) 그 종류의 목록을 **그 자리에서 다시 받아** 확인한 뒤 저장한다 — 목록에 없는 모델을 저장하지 않기 위해서다. 모델을 둔 채 끄기, 선택 해제, 한도 변경은 OpenRouter 없이 된다(장애 중에도 끌 수 있어야 한다).

## 2. 카탈로그 출처
| 종류 | 출처 | 근거 |
|---|---|---|
| 이미지 | `/api/v1/images/models` | 공식 문서(이미지 생성): `supported_parameters` 기술자, 가격은 엔드포인트 기록 |
| 음성 | `/api/v1/audio/speech/models` | 공식 문서(TTS): 출력 모달리티의 `supported_parameters` |
| 영상 | `/api/v1/videos/models` | 공식 문서(영상 생성): `supported_durations`·`pricing_skus` |
| 음악 | `/api/v1/models?output_modalities=audio` | 전용 목록이 문서에 없음. Lyria(`google/lyria-3-*`)는 일반 모델 목록에 출력 `audio`로 있다 — 출력에 `audio`가 없는 항목은 버린다 |

응답은 너그럽게 읽는다(모양이 다른 항목은 건너뛰고 추측하지 않는다). 가격은 목록에 있을 때만 보이고 없으면 "목록에 없음".

**가격 위치 (2단계에서 고침, OpenRouter 공개 OpenAPI 명세 `openrouter.ai/docs/openapi/openapi.yaml`·TTS 안내 문서, 2026-11-24).** 배포 뒤 실제 키로 열어 보니 이미지(71)·음성(38)·음악(4) 목록이 모두 "가격: 목록에 없음"이었다. 명세로 확인한 까닭과 고친 방법:
- 이미지: `ImageModelListItem.endpoints`는 배열이 아니라 **문자열**(`"/api/v1/images/models/<author>/<slug>/endpoints"`)이다. 가격은 그 URL의 `ImageModelEndpointsResponse.endpoints[].pricing: ImagePricingEntry[]`(`{billable: output_image|input_image|input_text|…, unit: image|megapixel|token|request, cost_usd: number, variant?}`)에만 있다. → 모델마다 그 기록을 읽는다(URL은 응답의 문자열이 아니라 id로 서버가 만든다, `author/slug` 모양만). 출력 이미지 줄이 있으면 그것만 보인다. 71개면 71번 읽기라 한 번에 6개·전체 20초로 묶고, 저장 전 재확인은 목록만 받는다.
- 음성: `SpeechModelResponse`·`SpeechModelEndpoint`에는 가격 필드가 **아예 없다**. TTS 문서: "per-character or per-second cost … via the Models API, where per-second models report their rate under `pricing.completion`". → `GET /models?output_modalities=speech`(`output_modalities`에 `speech` 값이 있다)의 `pricing`을 id로 맞춘다. 단위는 모델마다 다르다(TTS 문서는 글자·초를 말하지만 Gemini TTS는 입력 텍스트 토큰·출력 오디오 토큰 — 리뷰 1차). 응답에 단위가 없어 `입력 단위`·`출력 단위`와 "(단위 미확정)"으로만 표시한다.
- 음악: 일반 모델 목록의 `pricing`(`PublicPricing`: `prompt`·`completion`·`request`·`audio_output` 등 십진 문자열)을 읽는 것은 1단계와 같다. 다만 **Lyria의 곡당 가격**($0.08/song, 모델 페이지)은 명세의 어느 가격 필드에도 문서화돼 있지 않다 — 실제 응답에서 0이 아닌 값이 있으면 보이고, 모두 `"0"`이면 여전히 "목록에 없음"이다. 실제 키로 Lyria 항목의 `pricing`을 한 번 확인해야 한다(3단계 전 확인 과제).
- 표시: 아주 작은 단가가 `$6e-7`처럼 지수로 나오지 않게 소수로(유효 숫자 6자리).

**음악 목록의 음성 대화 모델 (1단계 이월).** `output_modalities=audio`에는 Lyria 같은 음악 모델과 GPT Audio 같은 음성 대화 모델이 섞인다. 명세의 `Model.supported_voices`(목소리 목록 또는 null)가 문서화된 구분점이다 — 목소리를 내놓는 모델은 대화용이다. 그런 모델은 빼지 않고(관리자가 정한다) "음성 대화 모델(음악 생성용 아님)"이라 표시하고 목록 끝에 둔다. 확정 판별은 아니다(음악 모델이 언젠가 목소리를 내놓으면 잘못 표시된다).

## 3. 키
- 관리자 키(암호화 저장) → `.env` `OPENROUTER_API_KEY` 순서, 요청마다 결정(`OpenRouterKeys`). 음성 전사 외부 대체도 같은 결정을 쓴다 — 키를 두 곳에서 따로 관리하지 않게.
- 저장 전 `/api/v1/key` 확인, 화면에는 끝 4자리와 남은 한도만. Cloudflare Access 토큰 등록(#36)과 같은 방식(호출 뒤 저장 직전 관리자 재확인, 쓰기는 한 번에 하나). 키와 확인 결과는 한 트랜잭션, 삭제는 한 문장(리뷰 1차) — 반쯤 바뀐 상태로 음성 전사의 과금 키가 바뀌지 않게.
- `.env` 키의 확인 결과는 저장하지 않고 프로세스 메모리에 그 키의 지문(SHA-256, 메모리에만)과 함께 둔다 — 운영자가 `.env` 키를 바꾸면 이전 잔액을 보여 주지 않는다. 카탈로그 캐시도 키 지문·키 변경 세대에 묶는다.

## 4. 비용과 사용량
- `usage_records` purpose `media`(텍스트 enum이라 마이그레이션 없음), runtime `openrouter`, `auth_type = api_key`, `priced_cost_micros` = OpenRouter가 알려 준 비용(가격표 없음). 그래서 기존 합계·오늘 비용 알림·월 예상에 그대로 들어간다. 생성마다 한 행(`<runId>#media:<callId>`), 같은 생성을 다시 쓰면 덮어쓴다.
- 하루 예산 `MediaBudget.remaining/allows`는 그 사람의 그날(서비스 시간대) `media` 행만 센다. 비용을 모르는 생성은 합에 넣지 않고 따로 센다 — 2단계에서 생성 직후 `/api/v1/generation?id=`로 비용을 채운다.

## 5. 청소년 계정과 요청 정책
- 숨기지 않는다(사용자 결정). 대신 모델이 moderation 값을 내놓으면 청소년 계정은 가장 엄격한 값을 보낸다(`moderationFor`). 값이 없으면 제공자 기본값. 정책은 고정(관리자 스위치 없음).
- 모든 요청에 `provider.data_collection: "deny"`(덮어쓸 수 없음), 나가는 글은 `carriesSecret` 검사. 영상은 ZDR이 지원되지 않아 `data_collection: deny`만 가능하다(이슈 본문).

## 6. 도구 (2단계)
- `image_generate`·`speech_generate`는 MCP 서버의 자체 도구(`packages/mcp-tools/src/media.ts`)라 Claude·Codex 런타임 모두 같은 도구 목록으로 본다. 스킬 권한이 아니라 **관리자의 종류 스위치**로 켜진다(켜짐 + 모델 + 키). 청소년 계정에도 보인다(사용자 결정). 예약 실행(스킬 범위가 있는 실행)에는 주지 않는다 — "사용자가 요청하지 않으면 부르지 않는다"를 서버가 지킬 수 있는 유일한 자리다.
- 동기 호출: 이미지·음성은 수십 초 안에 끝나 job이 필요 없다. 시간 한도 이미지 180초·음성 120초, Codex의 MCP 도구 시간 한도(`tool_timeout_sec`)를 늘리는 목록에 넣었다.
- **모델 기록은 호출마다 읽고, 읽지 못하면 보내지 않는다**(리뷰 1차): 처음에는 "모르면 그냥 보낸다"였지만, 그러면 청소년 moderation을 확인하지 못한 채 보내고 비용 상한도 없다. 이제 `media_lookup_failed`(재시도 가능). 관리자 화면의 캐시는 쓰지 않는다(도구 호출이 화면 캐시의 수명·키 세대에 묶이지 않게). 기록을 읽는 동안 관리자가 설정을 저장하거나 키를 바꾸면(설정 리비전·키 비교) 보내지 않는다(`media_changed`).
- 청소년 moderation: 이미지 요청 명세(`ImageGenerationRequest`)에는 `moderation` 필드가 없다(채팅의 이미지 생성 서버 도구 설정에만 `auto|low`). 그래서 **모델의 `supported_parameters`에 `moderation`이 있을 때만** 그 값 중 가장 엄격한 것을 최상위 매개변수로 보낸다(`supported_parameters`는 "그 엔드포인트가 받는 매개변수"). 기록을 확인해 없다고 나온 모델에는 보내지 않는다 — 제공자 기본값과 OpenRouter의 CSAM 검사가 적용된다.
- 목소리: OpenRouter TTS 문서는 일부 제공자가 공개 목록 밖의 사용자 정의·복제 목소리 id를 받는다고 한다. 그래서 voice는 **확인된 공개 목록에 있을 때만** 보낸다(목록이 없으면 지정 거부). 도구 입력에 참고 음성이 없고 `input_references`도 넣지 않는다.
- 음성은 `mp3`만 저장한다. PCM만 내는 모델(HeyGen, Gemini TTS)은 거부한다 — PCM을 WAV로 감싸는 것은 쉽지만 표본율이 모델마다 달라 문서로 확정되지 않았다.
- 이미지 출력 형식: 기록의 `output_format`이 래스터를 포함하면 png→webp→jpeg 순으로 명시해 요청하고, 벡터(SVG)뿐이면 돈을 내기 전에 거부한다. 관리자 목록에서도 표시하고 그 모델은 저장하지 않는다(실제 목록의 `recraft/recraft-v4-vector`가 예, 리뷰 1차).
- 비밀값: 사용자 글을 옵션 검사보다 **먼저** 검사한다(비밀값이 든 입력이 옵션 오류로 먼저 돌아가 다른 경로를 타지 않게). hint에 넣는 제공자 값은 영숫자 등 좁은 문법을 통과하고 비밀값이 아닌 것만. 도구 결과와 hint는 돌려주기 전에 한 번 더 가린다. 참고 이미지는 다시 인코딩하지 않고(새 의존성 없이) 메타데이터 청크·세그먼트를 구조적으로 버린 뒤, 남은 바이트의 출력 가능한 문자열을 검사한다 — 압축된 픽셀 자료에는 우연한 짧은 문자열만 있고, 파일에 써 넣은 비밀값은 출력 가능한 문자열로 남는다.

## 7. 예산 — 비용 상한 예약 (리뷰 1차 P1)
- 처음에는 이미지의 장당 가격만 메모리에 예약하고 음성은 0을 예약했는데, **음성 한 번으로도** $49.9999에서 $50.0002가 됐다. 그래서 모든 유료 호출이 **보수적인 최대 비용**(`media/cost.ts`)을 예약한다. 상한을 구할 수 없으면(출력 토큰 단가 이미지 모델, 음수 = 변동 가격, 기록 없음) 보내지 않는다(`media_no_price`).
- 예약은 메모리가 아니라 **사용량 행**이다: 예산 확인과 `reserveMedia`(행을 쓰고 `estimated_cost_micros`에 상한, 마이그레이션 `0038_media_estimate`)를 한 동기 단계로 해서 두 호출이 마지막 남은 예산을 함께 가져가지 못하고, 재시작해도 남는다. 예산은 `priced_cost_micros`(알려진 비용)가 있으면 그것, 없으면 상한을 센다 — 비용이 끝내 오지 않은 생성은 그날 상한을 계속 잡는다(예산을 넘기지 않는 쪽). 거절(4xx·5xx)은 과금되지 않으므로 행을 지우고, 연결 오류·시간 초과는 결과를 모르므로 남긴다.
- 상한을 잡는 방식: 단가의 단위가 응답에 적혀 있지 않으므로 **모든 해석을 덮는다** — 입력은 UTF-8 바이트(글자·토큰 어느 쪽도 넘지 않는다), 출력 음성은 가장 긴 길이(글자당 0.5초 + 30초)를 초당 50토큰으로 센다(Gemini TTS는 초당 32토큰; 초 단가여도 넘지 않는다), 이미지는 엔드포인트·변형 중 가장 비싼 값과 가장 큰 크기(8192²). 여유 1.2배. 초 단가 음성 모델은 예약이 실제의 수십 배일 수 있다 — 남은 예산이 적으면 그 모델은 거부된다(예약이 풀리는 것은 정산 때).
- 남은 한계: 같은 대화에 그사이 업로드가 들어와 파일 자리를 가져가면, 결제한 뒤 저장 때 `media_file_limit`이 날 수 있다(비용은 기록된다). 실제 비용이 상한을 넘는 일은 상한 정의상 없어야 하지만, OpenRouter가 기록에 없는 가격으로 청구하면(예: Lyria의 곡당 가격처럼 문서에 없는 필드) 넘을 수 있다 — 그 경우 다음 호출부터 막힌다.

## 8. 채팅 표시와 파일
- 생성 파일은 `files.addGenerated`로 실행의 답에 묶이고, 기존 `file_ref` 칩 흐름(`generatedFiles`)으로 답에 붙는다. 화면은 답의 `file_ref` 중 이름이 이미지·음성인 것을 미리보기·재생기로 보인다(사용자 첨부는 그대로 칩만).
- `INLINE_KINDS`에 webp·m4a·mp3·wav를, `FILE_CSP`에 `media-src 'self'`를 더했다. 나머지(`sandbox`, `default-src 'none'`, 스크립트 없음)는 그대로다. 앱 페이지의 CSP는 `default-src 'self'`라 `<audio src>`(같은 출처)가 이미 허용된다.
- 파일 원본 응답이 단일 byte range를 받는다(206/416, 권한 검사 뒤) — iOS Safari는 미디어를 Range로 받으며 이것 없이는 탐색이나 재생이 되지 않을 수 있다(Apple 안내). 여러 범위는 지원하지 않고 전체를 준다(RFC 9110 허용).
- WebP를 파일 종류에 더했다(이미지 모델이 자주 낸다). 업로드도 받는다(내용 서명 검사). 저장 종류는 응답이 주장하는 `media_type`이 아니라 바이트 서명으로 정한다.

## 9. 리뷰 2차 (#246)
- **가격 없음 ≠ 무료:** 1차의 상한 계산은 빈 가격 목록을 0으로 셌다(가짜 제공자로 $0.0001 남은 예산에서 $0.04가 승인됐다). 이제 명시적 0만 무료이고, 비었거나 필수 가격이 없거나 읽을 수 없거나 `-1`이 하나라도 있으면(기본과 `overrides` 키 합집합 전부, `Math.max`로 가리지 않는다) 상한 없음 → 거부.
- **참고 이미지 면적:** megapixel 입력 단가는 실제 폭·높이(파일 머리)로 예약하고, 8192² 픽셀을 넘는 참고 이미지는 거절한다 — 10MB 바이트 한도만으로는 면적 한도가 보장되지 않는다.
- **늦은 정산은 행에 남긴다:** 생성 id·정산 상태·시도 횟수를 사용량 행에 두고(메모리가 아니라서 재시작 후에도 이어 간다), 백그라운드 정산기가 백오프로 다시 조회한다. 끝내 확인하지 못한 행은 `unconfirmed`로 따로 남긴다 — 운영자가 OpenRouter 기록과 맞춰 볼 수 있게.
- **날짜 귀속:** 비용은 호출한 날의 것이다. 알림 검사도 그 날로 하고, 알림 중복 방지는 날짜 목록으로 바꿨다(한 값만 두면 전날을 알린 뒤 오늘이 다시 알려진다).
- **조회 "성공"의 정의:** HTTP 200이 아니라 모양이 맞는 기록이어야 한다. 청소년 계정의 moderation은 "있음(읽을 수 있는 값)" 또는 "없음(확인)"일 때만 보낸다.
- **키 세대 비교:** 키 문자열만 비교하면 A→B→A를 놓친다. 관리자 서비스의 키 세대를 생성기에 넘겨 함께 비교한다.
- **파서 방어:** 참고 이미지 파서는 구조를 검증하고(잘린 RIFF, 필수 청크) 조각 수·문자열 수에 상한을 둔다. 다시 인코딩하는 대안은 새 의존성(이미지 라이브러리)이 필요해 택하지 않았다.
- **음성 대체 금지:** 음성 도구가 없는 실행에는 "다른 방법(브라우저 speechSynthesis 등)으로 음성을 만들지 말고 꺼져 있다고 알린다"는 규칙을 지침에 넣는다. 템플릿이 아니라 도구 목록을 따르는 고정 문장이라 템플릿 버전(`common@11` 등)은 바뀌지 않고, 지침 해시는 바뀐다.

## 10. 리뷰 3차 (#246)
- **장별 올림:** 실제 면적만 더하면 작은 참고 이미지 여러 장에서 예약이 청구보다 작아진다(가짜 공급자로 $49.94 + $0.07 = $50.01 재현). 공급자의 최소 과금 단위를 문서로 다 알 수 없으므로 가장 흔한 규칙(장마다 올림, 최소 1MP — BFL)을 모든 megapixel 단가에 보수적으로 적용한다.
- **중단된 예약 복구:** id를 비용 조회 뒤에 쓰면 그 사이 중단될 때 id를 잃는다. 헤더를 받는 즉시 쓰고, 시작 시 이전 프로세스의 `reserved` 행을 정리한다. 이 프로세스의 진행 중 호출은 시작 시각 이후에 만든 행이라 건드리지 않는다(부트 id 열을 더하지 않은 이유).
- **길이 단위:** 비밀값 등록은 JavaScript 문자열 길이(UTF-16 단위)로 최소 길이를 재므로, 참고 이미지 검사도 UTF-16 단위로 센다.
- **마이그레이션:** 0038은 dev에 합쳐지지 않아 다시 만들었다(열 4개). 1차 PR 시점의 0038을 이미 적용한 검증용 DB가 있으면 그 DB는 다시 만들어야 한다(`duplicate column`).

## 11. 리뷰 4차 (#246)
- **시작 시 복구에서 시계를 뺐다.** 서버는 DB를 열기 전에 데이터 폴더의 배타 잠금을 잡으므로(storage/data-lock.ts) 같은 DB를 쓰는 서버는 하나뿐이다. 복구를 앱을 만드는 중(요청을 받기 전)에 동기로 하면 그 시점의 `reserved` 행은 모두 이전 프로세스의 것이다 — 시작 시각과 비교할 필요가 없고, 시계가 뒤로 가거나 같은 ms여도 빠지지 않는다. 진행 중 id를 메모리에 두고 주기 조회에 `reserved`를 넣는 대안보다 단순해서 택했다.
- **복구 실패 (5차에서 바꿈):** 두 상태 전환은 한 트랜잭션이다. 4차에는 실패하면 시작을 실패시켰지만, 사용자 결정(채팅 가용성이 미디어 비용 정리보다 우선)으로 5차에 바꿨다 — 서버는 시작하고, 복구가 성공할 때까지 새 유료 미디어 호출만 `media_recovering`으로 막으며 뒤에서 백오프로 다시 한다. 막음이 미디어 호출보다 먼저 걸리므로 새 예약이 복구 대상에 섞이지 않는다. 이로써 `buildApp`이 타이머·리스너를 등록한 뒤 예외를 던지는 경로도 없어졌다.
- **잠금 잡은 시작에서만 (5차):** 복구는 데이터 폴더 잠금을 잡은 서버 시작(`dataLock`)에서만 한다. 잠금 없이 같은 DB로 앱을 만들면(시험·도구) 다른 서버의 진행 중 예약을 `unconfirmed`로 바꿀 수 있기 때문이다. 시험은 격리된 DB에서 복구를 직접 부른다.
- **키 없는 주기:** 조회할 수 없으므로 포기할 행만 SQL로 골라 처리한다(첫 조회 행에서 멈추지 않는다).

## 12. 리뷰 6차 (#246)
- **뒤의 재시도는 이벤트 루프를 막지 않는다:** 5차의 재시도는 시작 시도와 같은 함수(최대 3번, `Atomics.wait` 200ms, SQLite 바쁨 대기 5초)를 써서 쓰기 잠금이 잡혀 있으면 타이머 한 번에 16초까지 서버 전체가 멈출 수 있었다. 이제 재시도는 타이머마다 한 번, `BEGIN IMMEDIATE`를 바쁨 대기 없이(그 동안만 `busy_timeout = 0`) 시도해 바로 성공·실패한다. 시작 시도는 요청을 받기 전이라 바쁨 대기를 그대로 두고, `Atomics.wait`는 없앴다.
- **잠금을 실제로 잡고 있을 때만:** `dataLock`이 있다는 것만으로는 부족하다(잠금이 풀린 핸들). 시작 시도와 매 재시도 전에 `held()`를 확인하고, 아니면 행을 건드리지 않고 미디어를 막아 둔다.

## 13. 긴 음성 스크립트 자동 분할 (#248)
- **왜:** 운영 모델 `elevenlabs/eleven-v4`(OpenRouter TTS)는 출력이 약 290초를 넘으면 오류 없이 끊긴다. 2단계는 한 번만 불러 긴 글이 잘린 채 저장되고 비용은 그대로 나갔다. 그래서 글을 나눠 합성하고 이어 붙인다(4단계 나레이션도 이것을 쓴다).
- **분할 기준 = 느린 읽기 속도 추정 240초:** 공급자의 끊김(290초)과 50초 여유. 정확한 길이는 목소리·`instructions`·숫자 읽기에 따라 다르므로, 조각 크기는 **느린** 속도(한국어 음절 초당 4.5, 영어 글자 초당 11)로 잡고 잘림 판정은 **보통** 속도(6.5, 15)와 비교한다. 두 속도를 나눈 이유: 하나로 하면 크기를 보수적으로 잡을수록 "예상보다 짧음" 판정이 느슨해진다. 숫자는 여러 음절로 읽혀 더 느리게 센다. 경계는 문단 → 문장 → 쉼표류 → 공백 → 글자 순(긴 문장 대체). 한 조각에 들어가는 글은 바꾸지 않고 그대로 보낸다(2단계와 같은 요청 — 기존 시험·동작 유지).
- **잘림 판정:** "280초 이상"(조각이 240초 이하이므로 290초 끊김을 잡는다)과 "보통 추정의 절반 미만"(추정 20초 이상만). 한 번 다시 나눠(자기 추정의 절반) 시도하고, 또 잘리면 실패 — 무한 재시도는 비용이 끝없이 나갈 수 있어 하지 않는다. 잘린 조각의 비용은 이미 나갔으므로 기록하고 결과 `costUsd`에도 넣는다.
- **조각별 사용량 행:** 한 호출의 조각마다 자기 행(자기 call id·generation id)을 둔다. 한 행에 여러 generation id를 합치는 방식은 마이그레이션(열 또는 별도 표)과 정산기·복구의 변경이 필요하고, 조각마다 정산 시점이 달라 부분 정산 상태가 생긴다. 조각별 행이면 2단계의 예약 → 2xx 헤더 즉시 id 기록 → 정산/늦은 정산 → 복구 흐름을 그대로 쓴다. 대가: 사용량 화면의 최근 요청 목록에 조각 수만큼 행이 보인다(같은 실행 id 접두사).
- **예산 = 합계 + 재시도 한 번의 여유, 재시도는 보내기 직전 다시 예약:** 모든 조각의 상한을 한 동기 단계에서 확인·예약해야 두 호출이 마지막 예산을 함께 가져가지 못한다. 재시도 조각까지 처음부터 모두 예약하면(조각 수만큼 두 배) 대부분의 정상 호출이 하루 한도에서 불필요하게 거부되므로, 처음 확인에는 "가장 큰 조각을 다시 나눴을 때의 상한"만 여유로 더하고(예약은 하지 않음), 실제 재시도 직전에 다시 확인·예약한다. 그사이 다른 호출이 예산을 쓰면 재시도가 `media_budget`으로 실패할 수 있다(파일 없음, 나간 비용은 기록) — 그 경우가 드물고 안전한 쪽이라 받아들였다. 보내지 않은 조각의 예약은 호출이 멈추면 지운다.
- **ffmpeg는 음성 전사의 것을 그대로:** 새 의존성 없이 `AUDIO_FFMPEG`(`ffmpegOf`)와 그 옆의 ffprobe를 쓰고(측정·저장 방식은 여러 번 바뀌었다 — 지금은 §13.9), 같은 샌드박스 규칙(자기 프로세스 그룹, 네트워크 없음, 자식 없음, 읽기 `in/`·쓰기 `out/`, 시간·메모리·출력 상한)으로 돌린다. 측정에 ffprobe를 쓴 이유: MP3 프레임을 직접 세면 ID3·Xing·VBR 변형을 다시 구현해야 한다. ~~이어 붙이기는 같은 스트림이면 스트림 복사, 다르면 재인코딩~~ (지난 결정 — 5차에 "늘 재인코딩", 6차에 "PCM에서 한 번 인코딩"으로 바뀜, §13.5·§13.6). 50MB를 넘으면 64 kbit/s 모노로 다시(말소리에 충분). 이은 결과의 길이를 조각 합과 비교해 이음매에서 잃은 부분이 없는지 확인한다. 조각 사이 무음은 넣지 않았다(문장 경계의 자연스러운 쉼으로 충분했다).
- **ffmpeg가 없을 때 (3차에서 바꿈):** 처음에는 한 조각 글을 2단계처럼 측정 없이 만들었지만, #248은 조각마다 길이를 재고 잘린 파일은 저장하지 않기로 정했다. 그래서 측정할 수 없는 서버(ffprobe·ffmpeg 없음, macOS 아님)에서는 한 조각 글도 **유료 요청 전에** 거부한다(`media_audio_unavailable`). e2e(FAKE_RUNTIME) 서버는 MP3 프레임 머리로 재는 가짜 ffprobe·ffmpeg를 쓴다.
- **한도:** 입력 12,000자(느린 추정으로 한국어 약 44분, 128 kbit/s면 약 42MB — 50MB 안), 조각 16개, 호출 30분(새 조각을 시작하지 않는 시점 — Codex 도구 시간 한도는 그 위로). 조각은 차례로 보낸다(동시에 보내면 빠르지만 공급자 속도 제한·취소·순서 처리가 복잡해지고, 실행당·사용자당 동시 생성 칸 규칙과도 맞지 않는다).
- **설정 변경·취소:** 조각마다 실행이 살아 있는지와 설정 리비전·키 세대를 다시 본다 — 30분까지 걸릴 수 있는 호출이 관리자가 끈 뒤에도 돈을 계속 쓰지 않게.

### 13.1 리뷰 1차 (#251)
- **보내지 않은 조각은 DB에서도 구분한다:** 처음에는 미전송 여부를 메모리에만 두어, 조각 처리 중 프로세스가 멈추면 시작 시 복구가 보내지도 않은 행까지 `unconfirmed`로 바꿔 쓰지 않은 돈이 그날 예산을 잡았다. 이제 예약은 `pending_send`, 보내기 직전에 `reserved`로 바꾸고, 복구는 `pending_send`를 지운다(같은 트랜잭션). `media_settlement`는 CHECK 없는 text 열이라 마이그레이션은 필요 없다(Drizzle의 enum은 타입에만 있다).
- **자정을 넘긴 호출:** 1·2차에 "보내기 직전 새 날로 옮기기"를 넣었으나 3차에서 걷어냈다 — §13.3.
- **정수 마이크로달러:** USD 합계를 한 번 올림한 값으로 확인하고 행마다 따로 올림하면 확인액이 예약액보다 작아질 수 있었다(검토에서 23 vs 32µUSD). 조각마다 정수로 바꾼 뒤 그 정수만 쓴다(`boundMicros`, `MediaBudget.allowsMicros`, `reserveMedia({estimateMicros})`).
- **조각마다 비밀값 검사:** 처음 계획의 검사 뒤에 다른 자격 증명이 비밀값 목록에 등록될 수 있다(30분까지 걸리는 호출). 그래서 조각마다 실제로 보내는 값을 그 순간의 목록으로 다시 검사한다 — 걸린 조각과 나머지는 보내지 않은 예약으로 지운다.
- **무엇을 제한하나:** "처음 나눈 조각 16개"(전송 전 — 비용 없음, `media_too_long`)와 "유료 요청 20번"(재시도 포함)을 따로 둔다. 재시도가 요청 상한을 넘기면 재시도하지 않고, 이미 비용이 나간 상태라 "비용 없음"을 말하는 `media_too_long`이 아니라 `media_truncated`에 비용이 기록됐다는 hint를 붙인다.
- **취소 신호:** MCP 진입점이 토큰 철회를 `AbortController`에 연결해(호출이 끝나면 구독 해제) 측정·이어 붙이기 중인 ffprobe·ffmpeg도 바로 죽는다. 토큰 저장소의 `onRevoke`는 "철회됐고 그 뒤 새 토큰이 없을 때"만 즉시 부른다 — 철회 뒤 다시 토큰을 받은 실행(시험에서 실행을 다시 여는 경우)은 다음 철회를 기다린다.
- **Codex 시간 한도:** 이어 붙이기는 50MB를 넘으면 한 번 더 돈다. 시간 한도는 서버가 지키는 같은 상수(호출 30분, 조각 120초, 측정 20초 × 2, 이어 붙이기 3분 × 2, 비용 조회)로 계산한다(`speechCallBudgetMs`).
- **분할 세부:** 공백 없이 붙은 문장 끝("했어요.그리고")도 경계로 보고(소수점은 제외), 강제 분할은 grapheme 경계에서만 한다(`Intl.Segmenter` — 결합 악센트·ZWJ 이모지). 원문 구간은 빠짐없이 덮고, 공백 정리는 보내는 값에서만 한다 — 둘을 따로 시험한다.
- **청소의 경로 확인:** 작업 폴더 루트가 링크이거나 DATA_DIR 밖을 가리키면 시작 청소가 그 아래를 지울 수 있었다(만들 때는 막았지만 청소는 확인하지 않았다). 이제 둘 다 같은 검사(링크 아님, 실제 경로 = `<실제 DATA_DIR>/speech-scratch`)를 하고, 청소는 `<uuid>` 실제 폴더만 통째로, 그 밖의 항목은 링크 자체만 지운다.

### 13.2 리뷰 2차 (#251)
- **시각은 한 번만 읽는다:** 예산 확인과 행 쓰기가 시계를 따로 읽어, 그 사이 자정이 지나면 자기 예약을 두 번 셌다. 2차에는 단계마다 시각을 한 번 읽게 했고, 3차에서 이를 "호출마다 한 번"으로 줄였다(§13.3).
- **철회 감시의 구독 해제:** 같은 실행 id가 철회된 뒤 다시 토큰을 받고 새 호출이 감시하면, 옛 호출의 해제가 새 감시 집합을 지웠다. 자기 집합일 때만 지운다.
- **요청 수:** 보내지 않은 조각은 요청이 아니므로 `request_count` 0으로 예약하고 보낼 때 1로 바꾼다(예약액과 "진행 중" 표시는 그대로).
- **약어·주소:** 공백 없는 마침표 + 대문자 규칙이 `U.S.A.`·`https://www.Example.COM`·`Dr. Smith`를 갈랐다. 마침표 앞 낱말이 주소·점 이니셜·흔한 칭호면 문장 끝으로 보지 않는다(공백 있는 경우도 같은 규칙 — "U.S. Army"·"Dr. Smith"). 대가: "…in the U.S. Then…"처럼 이니셜로 끝나는 실제 문장 끝도 경계가 되지 않는다(다음 경계에서 나뉜다).

### 13.3 리뷰 3차 (#251) — 하루 귀속을 다시 정함
- **결정: 일일 한도는 호출 시작일 기준.** 자정·일일 한도 지적이 1·2·3차 연속으로 나와, 덧대지 않고 가장 보수적이고 단순한 쪽으로 다시 정했다(PR·이슈 #248에 남김). 한 번의 도구 호출(음성의 모든 조각·재시도 조각, 이미지)의 비용은 모두 **호출의 첫 예약 시각**(`ctx.startedAt`)의 서비스일로 센다. 모든 행을 그 시각으로 쓰고, 예산 확인(처음·재시도)도 그날만 한다. 보내기 직전의 날짜 비교·새 날 잔액 확인·행 옮기기(`sendingMedia`의 move, `MediaBudget.dayOf`, 조각의 `day`)는 지웠다 — `sendingMedia`는 `pending_send` → `reserved`, 요청 수 0 → 1만 한다.
- **이유:** #248은 "호출 전에 조각 전체의 최대 비용을 합쳐 한 번에 예약"으로 정했다 — 호출 단위로 하루를 고정하는 것이 스펙에 가장 가깝다. 날짜를 옮기는 로직이 없어지므로 확인과 기록 사이의 경합 경로 자체가 없다. 한 번의 예약이 그 호출 모든 비용의 상한이라는 장치는 그대로다. 정산과 늦은 비용 알림은 행의 `created_at`(시작일)로 간다.
- **대가:** 자정 직전에 시작한 호출의 비용은 전날 한도로 계산된다. 자정을 낀 짧은 구간(최대 한 호출 길이, 30분 남짓)에는 두 날의 한도가 이어서 쓰일 수 있다. 하루 단위 한도의 정의를 "호출 시작일 기준"으로 문서에 적었다.
- **한 미디어 시계:** 미디어 행의 예약·갱신·복구(`UsageStore`의 `mediaNow`), 하루 예산, 생성기, 늦은 비용 정산기가 같은 시계를 쓴다. 시험이 시계를 한쪽에만 주면 예약과 정산기의 백오프가 서로 다른 시각을 봐서 행이 조회 없이 포기되거나 조회되지 않았다.
- **측정 없이는 만들지 않는다:** 위 "ffmpeg가 없을 때" 참고.
- **분할:** 공백·줄바꿈 뒤에 시작하는 주소는 앞 문장의 끝을 막지 않는다(오른쪽 주소 검사는 마침표 바로 뒤가 같은 낱말일 때만). 한 grapheme이 조각 목표보다 길어 나눌 수 없는 글은 계획 단계에서 거부한다(보내지 않는다).

### 13.4 리뷰 4차 (#251)
- **길이는 프레임으로 센다:** ffprobe의 `format.duration`은 Xing/Info 길이 헤더가 없는 VBR MP3에서 첫 프레임들의 비트레이트로 낸 추정값이다(실제 290.04초 → 108.29초, 잘림 검사를 통과해 저장됐다). 이제 `-count_packets`로 읽은 패킷(= MP3 프레임) 수에 프레임당 표본 수를 곱해 잰다 — 집계 숫자 하나라 출력이 작고, 디코딩하지 않아 빠르다. 조각과 이어 붙인 결과 모두. e2e·시험용 가짜(`fixtureSpeechAudio`)도 프레임을 하나씩 걸으며 세고(프레임마다 자기 비트레이트), 맨 앞의 Xing/Info 프레임은 세지 않는다.
- **문단 경계는 먼저, 무조건:** 주소 예외가 마침표 매치에 딸린 빈 줄까지 버려 두 문단이 이어지고 주소 한가운데서 잘렸다. 이제 빈 줄 문단 경계로 먼저 자른 뒤 그 안에서 문장을 자르고, 마침표 뒤에 줄바꿈이 있으면 주소여도 문장 끝이다.
- **주소 안은 자르지 않는다:** ASCII 쉼표·쌍점·쌍반점(`, : ;`)은 뒤에 공백이 있을 때만 절 경계다(`https:`·`3,000` 안에서 자르지 않는다; 전각 `，、；：`는 그대로 경계). 조각의 길이 추정은 보낼 값(양끝 공백을 뺀 글)으로 한다.
- **비용 정정의 알림 날짜:** `recordMedia`의 정정도 행의 `created_at`(호출 시작일)로 알림을 검사한다(`settleMedia`와 같게).

### 13.5 리뷰 5차 (#251) — 길이 측정을 다시 정함 (재계획 2)
- **결정: 실제 디코딩으로 잰다.** (1 kHz 8비트 PCM으로 바꿔 세는 방법은 §13.6에서 "원래 표본율로 끝까지 디코딩"으로 바뀜.) 길이 측정에서 P2가 3차(ffprobe 없음)·4차(VBR 추정)·5차(응답 안 표본율 변경 290.35초 → 104.76초, 머리글이 남은 손상 MP3 10.06초 → 실제 1.60초)로 연속 나와, 머리글·패킷 수로 계산하는 방식을 버렸다. 조각과 이어 붙인 결과 모두 ffmpeg로 끝까지 디코딩해 1 kHz 모노 8비트 PCM(1밀리초 = 1바이트)으로 내보내고 그 크기로 센다. 표본율이 바뀌어도 변환 뒤 표본으로 센다. 측정 하나는 최대 4시간 분량(14.4MB)·60초로 묶고, Codex 도구 시간 한도 계산에 넣었다. ffprobe·`-count_packets`·`mp3PacketSeconds`는 지웠다.
- **디코딩 오류 = 손상:** 엄격한 디코딩(`-xerror -err_detect explode`)에서 종료 코드가 0이 아니거나 오류 출력이 있으면 그 응답은 손상이다 — `media_audio_corrupt`, 비용 기록, 파일 없음, 재시도 없음(같은 손상을 다시 사는 것을 막는다). 깨끗하게 디코딩됐지만 짧은 응답만 재분할한다. 대가: 실제 공급자가 오류 수준 로그를 남기는 무해한 MP3를 내면 거부된다(지금까지 그런 응답은 관찰되지 않았다).
- **(지난 결정 — §13.6에서 바뀜) 이어 붙이기는 늘 재인코딩:** 조각 안에서도 스트림이 바뀔 수 있으므로 스트림 복사가 안전한지 판단할 근거(ffprobe의 스트림 정보)를 더 이상 믿지 않는다. 128 kbit/s 모노로 다시 인코딩한다(말소리에 충분). 한 조각이면 받은 그대로 저장한다.
- **경계 허용치:** 판정은 디코딩된 길이로 하며, 인코더 시작 지연·끝 패딩으로 생기는 약 0.2초 이내의 차이는 경계(280초, 추정의 절반)에서 허용한다 — 그 차이로 경계 바로 옆의 판정이 바뀌는 것은 결함으로 보지 않는다.
- **추정은 정수로 센다:** 글자 종류별 개수를 정수로 센 뒤 종류마다 한 번 나눈다(1/15를 300번 더하면 19.99999999999995가 되어 20초 기준의 짧음 검사를 건너뛰었다).
- **가짜도 같은 뜻:** e2e·시험용 `fixtureSpeechAudio`는 프레임을 하나씩 각자의 표본율로 걸어 "디코딩하면 나올 길이"를 세고, 프레임이 아닌 바이트가 섞이거나 시험용 표시가 있으면 손상으로 답한다.

### 13.6 리뷰 6차 (#251) — 받는 형식을 좁힘 (재계획 3)
- **왜:** 재계획 2(디코딩으로 잼) 뒤에도 측정·결합에서 P2가 나왔다 — 1 kHz로 바꿀 때 표본율이 바뀔 때마다 오차가 쌓임(280.908초 → 279.28초, 20ms 파일 → 0바이트), 표본율이 바뀌는 조각 뒤에서 결합이 다음 조각 0.34초를 잃음, `-t 4h` 뒤의 손상을 놓쳐 유료 재시도, MP2를 디코딩해 `.mp3`로 저장. "어떤 오디오든 받아 맞게 재려는" 설계가 원인이라 보고 **받는 형식을 좁혔다.**
- **결정 1 — 형식 고정:** MPEG-1/2/2.5 Layer III, 응답 전체에서 표본율 하나·채널 수 하나, 여러 조각이면 모두 같은 형식. 서버 코드가 파일 전체의 프레임 머리를 걷는다(`mp3.ts` — 머리만, 디코딩 없음; MP2·자유 형식·형식 변화·프레임 밖 바이트를 잡는다). 아니면 `media_audio_unsupported`(비용 기록, 파일·재시도 없음). 같은 모델·목소리·형식의 실제 TTS 응답은 형태가 일정하므로 정상 호출에는 영향이 없다고 본다.
- **결정 2 — 원래 표본율로 정확히, 저장은 묶음:** 리샘플링 없이 입력 끝까지(`-t` 없음) 엄격하게 디코딩해 null 출력으로 버리고, `-progress`의 `out_time_us`(= 표본 ÷ 표본율)로 표본 수를 정수로 센다. 출력은 진행 보고 몇 줄이라 묶여 있고, PCM은 저장하지 않는다. 디코딩한 표본은 프레임 수 × 프레임당 표본(위 한계)을 넘을 수 없다 — 넘으면 손상으로 본다. 다른 길(PCM을 파일로 써서 크기를 재기)은 조각당 최대 수십 MB·결합 결과는 수백 MB의 디스크를 쓰므로 택하지 않았다.
- **결정 3 — 조각 상한·측정 실패:** 디코딩한 길이가 조각당 600초를 넘으면 비정상 응답(재시도 없음) — 프레임으로 본 최대 길이가 이미 넘으면 디코딩하지 않는다. 샌드박스·프로그램 시작 실패(sandbox-exec 종료 71 등), 시간·메모리 한도는 `media_measure_failed` — 손상과 구분한다. 손상 통합 시험은 같은 환경에서 정상 대조 파일이 먼저 디코딩되는지 확인한다(샌드박스가 안 되는 환경에서 손상 시험이 우연히 통과하지 않게).
- **결정 4 — 결합은 PCM에서:** 조각마다 같은 PCM(s16 모노, 한 표본율)으로 디코딩해 차례로 잇고 한 번 인코딩한다 — ffmpeg 하나의 필터 그래프 안에서(디스크에 PCM을 쓰지 않음). 결과는 조각 표본 수의 정확한 합과 인코더 지연·패딩 수준(0.1초 + 조각당 0.01초) 안에서 맞아야 한다. 시험은 마지막 조각의 식별음(1 kHz)이 끝까지 남는지 본다.
- **추정 비교는 마이크로초 정수:** 추정을 마이크로초로 반올림하고, 잘림 판정(짧음 검사 진입 20초, 280초, 절반)도 마이크로초 정수로 비교한다 — 한글 52·숫자 39·기타 50자 = 정확히 20초가 짧음 검사에 들어간다.

### 13.7 리뷰 7차 (#251) — 역할을 줄임 (재계획 3 보정)
- **왜:** 7차의 지적 대부분은 직접 만든 MP3 판독기가 맡은 일이 너무 많고(정상 APEv2 태그, 프레임 안의 `Info`·`TAG` 문자열을 손상으로 판정, 프레임 수로 599.49초 응답을 600초 초과로 미리 거부) 결합 허용치가 너무 빡빡해서(같은 프레임을 이은 8 kHz 여섯 조각이 0.37초 차이로 버려짐) 생겼다. 새 장치를 더하지 않고 역할을 줄였다.
- **판독기는 형식만:** `walkMp3`는 Layer III 여부와 표본율·채널의 일관성만 본다. 태그·프레임이 아닌 바이트는 건너뛰고, 손상 판정은 ffmpeg의 엄격한 디코딩에만 맡긴다. 디코더처럼 동기를 맞춘다 — 머리 다음 자리에 머리가 이어질 때만 프레임으로 보고(맞물리지 않은 곳에서는 두 개 더 이어져야), 맞물린 뒤에는 프레임 안을 보지 않는다.
- **표본 수는 디코딩된 표본:** `-progress`의 `out_time_us`는 타임스탬프로 계산돼 실제 표본 수와 어긋났다(969,536 vs 970,031). `astats`가 센 디코딩된 표본 수(정수)를 쓴다. 보고가 없거나 하나가 아니면 측정 실패.
- **600초 상한은 디코딩된 표본으로만.** 프레임 수로 미리 거부하지 않는다(크기 50MB 상한과 측정 시간 한도가 디코딩 양을 묶는다).
- **결합 허용치는 큰 손실만:** 1초 + 조각당 0.25초로 되돌렸다. 결합 결과를 재지 못하면 `media_measure_failed`(비용 기록 안내).
- **기준 형식:** 처음 측정에 성공한 응답의 형식을 잘림 검사 전에 고정한다 — 잘려 버린 첫 응답(22.05 kHz) 뒤 다른 형식의 재시도 응답(44.1 kHz)도 `media_audio_unsupported`.
- **오류 분류:** 메모리 부족(ENOMEM, 종료 244)·외부 신호는 측정 실패. 모델 사전 검사를 통과한 모델이 MP3가 아닌 응답(WAV 등)을 내면 모델 설정 오류(`media_unsupported_model`)가 아니라 `media_audio_unsupported`(비용 기록 안내).
- §13.6의 "프레임으로 본 최대 길이로 미리 거부", "`out_time_us`로 표본 수", "결합 허용치 0.1초 + 조각당 0.01초", "프레임 밖 바이트·잘린 마지막 프레임은 손상"은 이 절로 바뀌었다.

### 13.8 리뷰 8차 (#251) — 우리 해석층을 없앰 (재계획 4)
- **왜:** 재계획 3 뒤에도 6·7·8차에 측정 줄기의 P2가 이어졌고, 원인 대부분은 직접 만든 부분이었다 — MP3 판독기(태그 경계, 짧은 파일, 선두 태그)와 ffmpeg 로그 문자열 해석(메타데이터의 `[error]`·`exec`를 오류로 오인, `astats` 줄 파싱). 그래서 직접 해석하는 부분을 없애고 디코더가 보고하는 값만 쓴다.
- **결정 1 — 형식과 표본 수는 ffprobe의 프레임 보고값:** `-show_entries stream=…:frame=stream_index,channels,nb_samples,duration -of json`으로 모든 스트림과 디코딩된 오디오 프레임을 받아 **JSON 구조로** 판정한다. mp3 오디오 스트림 하나(첨부 그림 밖의 다른 스트림 없음), 모든 프레임이 한 표본율(`nb_samples × 분모 = 표본율 × 길이 × 분자`로 정확히)·한 채널 수, 표본 수는 `nb_samples`의 정수 합. ffprobe의 프레임 보고는 디코더 출력이라 인코더 지연·패딩이 이미 빠져 있다(10초 CBR 441,000표본, 첫 프레임 47·끝 프레임 889표본처럼). 이은 결과도 같은 방법으로 재므로 양쪽 셈이 같다. 보고 크기는 길이에 비례한 상한(초당 50프레임 × 100바이트 + 256KB)으로 묶는다. 직접 만든 판독기(`mp3.ts` `walkMp3`)와 `astats`·`decodedSamples`·로그 수준 해석을 지웠다. 저장 전 바이트 검사(`isMp3`)도 쓰지 않는다 — 형식은 디코더 판정 하나로.
- **결정 2 — 손상은 종료 코드로만:** 엄격한 ffmpeg 디코딩(`-xerror -err_detect explode`, null 출력)의 종료 코드와 실행기 보고(시작 실패·한도·중단·신호)로만 판정한다. 측정 실패: 실행기 시작 실패, 한도·중단 종료, 신호, 종료 코드 71(sandbox-exec)·126·127·244(ENOMEM)·255(ffmpeg가 신호를 받아 끝냄 — 실행기는 신호를 보지 못하므로 코드로). 그 밖의 0이 아닌 종료는 손상. 로그는 분류에 쓰지 않는다.
- **결정 3 — 저장:** 한 조각 원본은 받은 그대로 저장한다(선두 APEv2가 있는 mp3도). 파일 저장(`addGenerated`)은 내용을 다시 검사하지 않으므로 다시 먹싱할 필요가 없었다 — 더 작은 변경.
- **가짜:** `fixtureSpeechAudio`는 자기 작은 프레임 모형(`fixtureMp3Frames`)으로 같은 뜻을 흉내 낸다(시험·FAKE_RUNTIME 전용; Xing/Info는 신경 쓰지 않고 오디오로 센다 — 운영은 디코더가 정확히 센다).
- §13.6·§13.7의 "직접 만든 판독기로 형식 확인", "`astats`/`out_time_us`로 표본 수", "로그 수준(`[error]`)으로 손상", "저장 전 `isMp3`"는 이 절로 바뀌었다. 결합(PCM에서 한 번 인코딩, 허용치 1초 + 조각당 0.25초)과 기준 형식·조각 상한은 그대로다.

### 13.9 리뷰 9차 (#251) — 저장 파일은 늘 서버가 만든다 (재계획 5)
- **왜:** 받은 응답의 형식을 하나하나 판정하는 방식(재계획 3·4)은 새 혼합 형태가 나올 때마다 구멍이 생겼다 — 짧은 표본율 변경(ffprobe 프레임 길이가 모두 같아 290.05초가 267.77초로), MP3→MP2→MP3, MP3를 담은 WAV·MP4를 `.mp3`로 저장, 구형 ffprobe(5.1.7)의 프레임 필드 차이, 선두 APEv2 파일을 다시 첨부할 수 없음.
- **결정 1 — 늘 다시 인코딩:** 받은 응답은 조각이 하나여도 엄격하게(`-xerror -err_detect explode`) 끝까지 디코딩해 호출 표본율(첫 응답의 스트림 표본율)의 모노 s16 PCM으로 작업 폴더에 쓴다. 표본율이 바뀌면 ffmpeg가 변환한다. 길이는 PCM 크기의 정수 표본 수로, 잘림·600초 상한·결합 비교에 같은 값을 쓴다. 저장은 그 PCM을 서버가 인코딩한 mp3 하나(한 조각 192k, 여러 조각 128k, 50MB 넘으면 64k) — 공급자 원본 바이트는 저장하지 않는다. 디코딩 한 번이 손상 검사와 정확한 길이를 함께 맡아, 재계획 4의 별도 엄격 디코딩과 ffprobe 프레임 보고를 대신한다.
- **결정 2 — 받은 응답의 최소 조건:** ffprobe의 컨테이너·스트림 수준 필드만 본다(`format_name`·스트림 종류·코덱·표본율·첨부 그림 — 버전 간 안정적): 컨테이너 mp3, 오디오 스트림 하나, 코덱 mp3, 다른 스트림은 첨부 그림만. 오디오가 없거나(PNG 등) 다른 컨테이너·코덱이면 `media_audio_unsupported`. 프레임 단위 판정(`judgeProbe`, `probeOptions`, `probeOutputBytes`)은 없앴다. 응답끼리·응답 안의 표본율 차이는 거부하지 않고 변환한다(기준 형식 검사도 없앴다).
- **결정 3 — 출력량 과금 음성 모델 거부:** 출력(오디오 토큰·초)에 가격이 있는 음성 모델은 한 호출의 비용 상한을 글자 수로 정할 수 없다(한 글자 + 90초 발화 지시로 예약 $0.0183, 정산 $0.0288). #246의 출력 토큰 단가 이미지 모델처럼 상한 없음으로 보고 전송 전에 거부하고(`media_no_price`, 전용 안내), 관리자 화면에서 고를 때도 막는다(`media_model_output_priced` — 저장 때 그 모델의 엔드포인트 가격을 읽어 확인). 입력(글자·토큰) 기준 가격 모델만 쓴다. 음성 상한 계산의 출력 길이 추정(`SPEECH_SECONDS_PER_CHAR` 등)은 지웠다.
- **손상 판정:** 재계획 4와 같이 종료 상태로만.
- **다시 첨부:** 저장 파일이 늘 서버가 만든 mp3이므로, 선두 APEv2 같은 원본 형태 때문에 내려받은 파일을 다시 첨부하지 못하는 일이 없다 — 파일 형식 검사(`files/detect.ts`)는 바꾸지 않았다.
- **대가:** 한 조각도 다시 인코딩하므로 원본보다 음질이 아주 조금 떨어질 수 있다(192k로 줄임). 조각 PCM이 디스크를 잠시 쓴다(48 kHz 240초 조각 약 23MB, 인코딩 뒤 바로 지움).
- **가짜:** `fixtureSpeechAudio`는 같은 뜻을 단순하게 흉내 낸다(프레임 표본을 호출 표본율로 바꾼 만큼의 PCM, 인코딩은 그 길이의 무음 프레임). 디코더의 지연·패딩 제거는 흉내 내지 않으므로 경계 값 시험은 실제 디코더로 확인한 표본 수를 쓴다.
- §13.6–13.8의 "기준 형식(표본율·채널) 불일치 거부", "한 조각은 받은 그대로 저장", "결합은 조각 mp3를 ffmpeg 하나에서 PCM으로 디코딩해 잇기", "ffprobe 프레임 보고로 표본 수"는 이 절로 바뀌었다.

### 13.10 리뷰 10차 (#251)
- **50MB는 저장 파일에만:** 공급자 응답 합에 50MB를 걸어, 128 kbit/s 응답 13개(53MB)가 모두 결제된 뒤 인코딩하지 못했다. 이제 응답마다 50MB까지 읽고(HTTP 읽기 한도), 50MB 판정은 서버 인코딩 결과에만 한다(128k → 64k). 남는 조각 ≤ 20 × 280초 미만 × 64 kbit/s ≈ 45MB라 64k면 늘 들어가므로 미리 검사하지 않는다.
- **변환 손실:** 호출 표본율(8 kHz)로 변환하면 응답 안의 잦은 표본율 변경에서 음성을 잃었다(290초 → 267초, 잘림 검사 통과). ffmpeg의 `aresample=…:async=1:first_pts=0`은 오히려 길이를 망가뜨려(시험에서 수만 초) 쓰지 않았다. 다른 표본율에서 변환한 응답은 자기 표본율로도 한 번 더 디코딩해 그 길이로 판정하고, 두 길이가 0.25초보다 다르면 `media_audio_unsupported`(저장·재시도 없음). 같은 표본율의 응답은 한 번만 디코딩한다.
- **`concat:`과 `|`:** 데이터 폴더 경로에 `|`가 있으면 절대 경로 목록이 잘렸다. 인코더를 `out/`에서 실행하고 서버가 만든 PCM 이름(`pcm-N.s16`)만 넘긴다.
- **저장과 호출의 같은 가격 판정:** `speechPricing`(그 모델의 기록인지, 엔드포인트가 있는지, 출력 과금인지, 상한이 있는지)을 관리자 저장과 호출이 함께 쓴다. 저장 때 거부 이유를 보인다(`media_model_output_priced`, `media_model_no_price`).
- **자원 오류:** PCM 쓰기의 ENOSPC(228)·EFBIG(229)도 측정 실패.
- **가짜:** 다른 계층이 섞인 응답은 가짜가 실제 디코더처럼 셀 수 없어 지원하지 않음으로 답한다(실제 디코더 시험이 그 경우를 본다).

### 13.11 리뷰 11차 (#251)
- **늘 독립적인 두 번째 디코딩:** 응답의 스트림 표본율이 호출 표본율과 같으면 두 번째 디코딩을 건너뛰어, 8 kHz로 시작해 44.1/48 kHz가 번갈아 나오는 응답(변환 전 프레임별 재생 길이 합 291.278초, 8 kHz 스트림 표본율로 변환한 길이 268.153초)이 줄어든 길이로 저장됐다. 이제 모든 응답을 다른 표본율로 한 번 더 디코딩해 비교한다(호출 표본율과 다른 응답은 자기 표본율로, 같은 응답은 48 kHz — 호출이 48 kHz면 44.1 kHz). ffprobe의 패킷 길이를 더 싼 독립 출처로 검토했지만 프레임마다 정확하지 않았다(48/32 kHz가 섞인 파일에서 모든 패킷이 한 길이로 보고됨) — 쓰지 않는다. 대가: 측정마다 디코딩이 한 번 더(시간 한도 계산에 반영).
- **응답 쓰기 실패:** 공급자 응답을 작업 폴더에 쓰지 못하면(ENOSPC 등) 경로가 담긴 원래 예외 대신 `media_measure_failed`(비용 기록 안내).

### 13.12 리뷰 12차 (#251)
- **(지난 결정 — §13.13에서 지움) 프레임 머리 길이로 한 방향 교차 확인:** 48 kHz로 시작해 8/16 kHz 프레임이 번갈아 나오는 응답(프레임별 재생 길이 합 287.028초)은 두 디코딩(48 kHz 279.114초, 44.1 kHz 279.144초)이 같이 음성을 잃어 0.25초 비교를 통과했다. 그래서 프레임 머리 길이가 디코딩 길이보다 1초 넘게 길면 거부하는 확인(`headerSeconds`)을 두었으나, 13차에서 정상 파일 두 가지를 잘못 거부해 지웠다.
- 측정값(참고): prefix-1.mp3는 호출 8 kHz 변환 268.153초와 48 kHz 디코딩 289.242초의 차이로 0.25초 비교에서 거부됐다(48 kHz 289.242초와 44.1 kHz 289.125초의 차이는 0.117초로 그 자체로는 통과).

### 13.13 리뷰 13차 (#251) — 정리 후 머지 (사용자 결정)
- **프레임 머리 길이 교차 확인 제거:** 정상 파일 두 가지를 잘못 거부했다 — ffmpeg MP3 먹서가 큰 시작 지연·끝 패딩(4,529·3,471표본)을 기록한 8 kHz 파일(디코딩 7.208초, 머리 합 8.280초)과, ID3v2 갱신 태그에 미리듣기 MP3가 든 파일(머리 합이 두 배). `mp3-length.ts`·`HEADER_LOSS_S`·그 다시 읽기를 지웠다. 두 파일은 회귀 시험으로 남겼다(받아들임, 길이는 디코딩 길이).
- **남은 비교:** 측정마다 두 번 디코딩한다 — 호출 표본율로, 그리고 그 응답의 스트림 표본율이 다르면 그 표본율로, 같으면 48 kHz(호출이 48 kHz면 44.1 kHz)로. 두 길이가 0.25초 넘게 다르면 변환 손실(`media_audio_unsupported`, 형식 거부와 다른 안내).
- **측정 중 I/O 오류:** 측정·인코딩 결과 읽기가 실패하면 원래 예외(작업 폴더 경로 포함) 대신 `media_measure_failed`(비용 기록 안내).
- **알려진 한계 (확정 사항 — 범위 밖):** 프레임마다 표본율이 바뀌는 인위적·비정상 공급자 응답은 두 디코딩이 똑같이 음성을 잃을 수 있고, 그러면 길이가 조금 짧게 재어진 채 저장될 수 있다(예: 280.344초 → 279.507초). §13.12의 common-loss·prefix-1 같은 응답도 두 디코딩이 일치하면 이제 통과할 수 있다. 같은 모델·목소리·형식의 실제 TTS는 이런 응답을 내지 않는다. 머지 전 Codex로 한 번 확인하고(정상 응답 오거부·회귀 없음), 배포 뒤 실제 eleven-v4로 긴 스크립트를 시험한다.

## 14. 3단계 — 영상 생성 (확인 카드·비동기 작업)
- 날짜: 2026-11-26. 근거: 사용자 확정 사항(이슈 #238 댓글, 2026-11-26), 기술 계획과 그 계획 리뷰(Codex 1회, 11항목), OpenRouter 영상 문서(영상 생성 안내·API 참조·`/videos/models` 실제 목록 2026-11-26 사본). 운영: `docs/ops.md` §51.8.
- **범위:** 영상만. 음악(Lyria)은 요청·응답 형식과 곡당 가격이 문서로 확인되지 않아 뺐다(이슈 본문의 "확인되지 않으면 이 단계에서 뺀다"). 웹훅, 4K(그리고 2K), 첫 프레임 이미지(`frame_images` — 공개 URL 없이 보낼 수 있는지 별도 조사), 완료 뒤 에이전트 자동 후속 응답, 승인 후 취소(OpenRouter에 취소 API가 없다)는 하지 않는다.

### 14.1 왜 카드인가
영상은 한 번에 수 달러가 들 수 있고 몇 분 걸린다(비동기 API). 그래서 도구 호출은 **돈을 쓰지 않는다** — 확인 카드(`video_jobs` 행)만 만들고, 대화 주인이 카드에서 모델·길이·해상도·화면비·소리·예상 최대 비용을 보고 승인해야 제출한다(일정 제안 카드 #55와 같은 모양). 모델에게는 "아직 만들지 않았다, 카드를 확인하라고 말하라"고 결과와 설명으로 알린다.

### 14.2 비용 상한 (리뷰 1항, P1)
- 초당 가격만 받는다(사용자 결정 1). `video_tokens`(Seedance)는 길이로 상한을 낼 수 없어 관리자 저장에서 거부한다.
- 상한 = 선택 해상도에 **적용될 수 있는** 초당 SKU 전부의 최대값 × 길이(최소 금액 이상) × 1.2. "적용될 수 있는": 그 해상도 접미사이거나 접미사가 없는 것, 소리 있음·없음(서버가 `generate_audio`를 보내지 않으니 어느 쪽이든)·`long_`(긴 길이 요금)·`reference_` 변형 모두. 문서: "720p 전용 SKU가 없으면 접미사 없는 SKU" — 최대값이면 그보다 작지 않다.
- 보내지 않는 입력의 SKU만 뺀다(이미지·참조 이미지·영상 입력·이어 만들기). **그 밖에 해석 못 하는 SKU가 하나라도 있으면 상한 없음** — 관리자 저장·카드 생성·승인 모두 거부(모르는 단위를 0으로 보지 않는다, §7과 같다).
- 보수적 선택: `reference_duration_seconds*`(참조 영상 요금, HeyGen)은 우리가 참조를 보내지 않지만 초당 단가라 **최대값에 넣는다**(빼는 것보다 상한이 크다).

### 14.3 승인의 원자성 (리뷰 2·3항, P1)
- 모델 기록 다시 읽기(비동기)를 **먼저** 하고, 그 뒤 하나의 동기 구간·하나의 `BEGIN IMMEDIATE` 트랜잭션에서: 카드 상태·버전, 세션·활성 사용자·리소스 권한, 설정 리비전·모델·키 표식, 만료, 동시 작업 수(DB 기준, `submitting`·`pending`·`in_progress`·`downloading`), 파일 자리, 하루 예산(승인 시각 하나)을 확인하고 `reserveMedia(state: "video_job", at)`와 `UPDATE … WHERE status='awaiting_approval' AND version=?`(1행일 때만)를 함께 쓴다. 이중 승인은 버전으로 막는다(사용자 결정 3).
- 가격이 카드보다 오르면 같은 버전 조건으로 카드를 새 금액으로 고치고(버전 + 1) 보내지 않는다. 내렸으면 카드에 보인 금액을 그대로 예약한다(더 큰 쪽).
- 파일 자리: 승인된 작업은 결과 파일 자리 하나를 **영속으로** 잡는다 — 업로드와 다른 생성 파일의 insert 문이 그 자리를 함께 센다(`VIDEO_HELD`). 메모리만으로 잡으면 재시작 뒤 결제한 영상의 자리가 없어질 수 있다.

### 14.4 완료와 멱등성 (리뷰 4항, P1)
- 완료 응답의 `usage.cost`는 다운로드 **전에** 정산·영속한다. 파일은 파일 쓰기 잠금 안에서 작업이 아직 `downloading`이고 파일이 없는지 다시 보고, 파일 행·`file_id`·`done`을 **한 트랜잭션**으로 쓴다(작업당 파일 하나 — 같은 작업이 두 번 저장되지 않는다).
- 알림은 한 번만: 발행되거나 영구 거절되면 `notified_at`, 일시 실패면 행별 재시도(§14.11). `dedupeKey video:<id>:end`로 행은 하나.

### 14.5 대화 삭제·재시작 (리뷰 5항, P1; 사용자 결정 3·5)
- 대화 삭제 트랜잭션(`onDelete` 훅) 안에서 그 대화 작업의 `video_job` 예약을 모두 정리한다 — 거절로 끝난 작업의 미해제 예약은 삭제(과금 없음), 나머지는 `unconfirmed`(상한 유지, "비용은 남음"), 정산된 비용은 그대로. 커밋 뒤 진행 중 요청·다운로드를 중단한다. 작업 행은 FK cascade로 사라지고, 모든 갱신은 `WHERE id=? AND status IN (...)`라 사라진 작업에는 아무것도 쓰지 않는다.
- 재시작: `submitting`(요청을 보냈는데 응답 전에 죽었을 수 있음)은 **다시 보내지 않고** `video_unconfirmed`, 비용 최대치 유지(사용자 결정). 나머지 진행 중은 이어서 확인한다. 미디어 복구와 엔진의 시작 복구가 끝나기 전에는 승인하지 않는다(`video_recovering`). 기존 `recoverReservedMedia`·정산기는 `video_job` 행을 건드리지 않는다(영상의 `/generation?id=` 지원은 확인되지 않았다).

### 14.6 보안 가드 (리뷰 6–8항)
- 비밀값: 등록된 비밀값과 구성 비밀값(`.env`)으로 사용자 글(옵션 검사 전), 보낼 본문 전체(모델·옵션·URL 포함)를 카드 저장 직전과 **제출 직전**에 검사한다 — 그사이 등록된 비밀값이면 카드를 보내지 않고 끝낸다(`video_blocked`, 비용 없음). `video_jobs.prompt`는 쓸 때 가리고 재가림 대상이다.
- 권한: 카드 GET·SSE·승인·닫기 모두 리소스 권한(대화 주인만 — 보수적 선택: 공유받은 사람에게는 카드를 보이지 않는다, 비용과 프롬프트가 있으므로). 승인의 예약 단계 안에서 세션·활성·권한을 다시 본다. 열린 SSE는 접근이 끝나면 닫는다(`watchAccess`).
- URL: 제출은 고정 `/videos`, 상태·콘텐츠는 검증한 원격 id(`^gen-vid-\d+-[0-9A-Za-z]{20}$`)로만 만든다 — 응답의 `polling_url`·`unsigned_urls`·서명 `urls`는 쓰지 않는다. 키는 `Authorization`에만, 리다이렉트는 따라가지 않는다(`redirect: "manual"`로 받아 리다이렉트면 실패 — 영상을 다른 곳에서 받지 않는다). 상태 GET은 상태 코드와 `Retry-After`를 보존한다(429 백오프, 404 = 작업 없음).
- MP4: ffprobe(샌드박스)로 MP4 계열 `format_name` + MP4 `major_brand`(QuickTime 제외) + 영상 스트림 1개 이상. 서버가 바이트를 직접 해석하지 않는다(음성 재계획 5와 같은 원칙). ffprobe가 없으면 **유료 제출 전에** 승인을 거부한다. 인라인 제공은 `INLINE_KINDS`를 넓히지 않고, `video_jobs.file_id`로 확인되는 완료 작업의 파일만.

### 14.7 키 표식·사용량 상태 (리뷰 9항, P2)
- 키 세대(`<프로세스>:<변경 수>`)는 재시작하면 바뀌어 승인 대기 카드가 모두 만료된다. 그래서 키 저장·삭제마다 새로 쓰는 무작위 `media.key_revision`을 두고, 카드·작업에는 표식 `<admin|env>:<토큰>`을 저장한다(키·키에서 나온 값은 저장하지 않는다; 표식은 되돌아가지 않는다 — §14.11). 남은 한계: `.env`의 키 값만 바꾸고 재시작하면 표식이 같다 — 대기 카드는 만료되지 않고 진행 중 작업은 새 키로 확인한다(다른 계정이면 404가 마감까지 이어져 `video_timeout`, 상한 유지).
- 사용량 상태 `video_job`(텍스트 열이라 마이그레이션 없음): 예약 중인 영상 작업. 사용량 화면에서 "진행 중"(`isPending`), 끝나면 `settled` 또는 `unconfirmed`(`unconfirmVideoMedia`는 `video_job`일 때만 바꾼다 — 정산된 비용을 덮지 않는다).

### 14.8 카드 옵션 (리뷰 10항, P2)
- 길이: 기본은 관리자 기본 길이(8초) 이하 지원값 중 최대(없으면 최소), 요청하면 그 이상 중 최소(없으면 최대). 해상도: `<n>p`, n ≤ 1080만(2K·4K·1K 제외 — "1K"가 몇 픽셀인지 문서에 없다), 기본 720p(없으면 가장 낮은 것). 1080p 이하 해상도나 길이 목록이 없으면 카드를 만들지 않는다. 화면비 목록이 없으면 보내지 않는다(가격과 무관 — 모델 기본값).
- 소리: `generate_audio`(true/false/null)로 켜짐·꺼짐·확인 안 됨을 보인다. 보내지 않는다.
- 승인 때 같은 조합이 여전히 있는지 본다(없으면 만료 — 자동으로 다른 값으로 바꾸지 않는다).

### 14.9 시간·디스크 (리뷰 11항, P2; 사용자 결정 4·5)
- 마감은 승인 시각 + 60분으로 고정하고(제출 직전 — 실제 제출보다 이르다), 각 요청 시간 한도와 백오프를 남은 시간으로 자른다. 작업마다 따로 돈다(한 다운로드가 다른 작업의 확인을 막지 않는다).
- 결과는 50MB를 넘어도 받는다 — 영상 작업 결과에만, 디스크 보호 상한 1GB로 스트리밍(4K를 막으므로 실제로는 훨씬 작다). 부분 파일은 중단 때와 엔진 시작 때 지운다.

### 14.10 남은 위험
- **카탈로그는 모델당 한 엔드포인트 기준**(OpenRouter 문서)이다. 명시적 공급자 라우팅을 하지 않으므로 다른 공급자로 가면 가격·지원 옵션이 다를 수 있다 — 상한이 실제보다 작을 수 있는 유일한 경로다. 1.2배 여유와 다음 호출 차단으로 막는다.
- **실패한 작업의 과금:** 문서상 실패·취소·만료는 보통 과금되지 않지만 "검열로 막힌 출력에 과금하는 공급자"가 있어 `usage` 없이 과금될 수 있다. 그래서 상한을 유지한다(사용자 결정) — 실제로 과금되지 않았다면 그날 예산을 그만큼 덜 쓰게 된다.
- **5xx 제출:** 작업이 시작됐을 수 있지만 id가 없어 추적할 수 없다. 다시 보내지 않고 최대치를 남긴다 — 실제로 만들어진 영상은 받지 못한다.
- **완료 직후 다운로드 실패:** 409·429·5xx는 마감까지 다시 받고, 그 밖(4xx·리다이렉트)이나 마감 초과면 실패 — 이미 정산된 비용은 남는다. OpenRouter의 사본은 `expires_at`까지만 있다.
- **MP4 확인은 형식만:** 일부러 만든 MP4(조작된 상자, 악성 코덱 데이터)의 정밀 대응은 범위 밖이다(사용자 결정). 브라우저의 `<video>`가 디코딩한다 — 파일 응답의 CSP(`sandbox`, `default-src 'none'`, `media-src 'self'`)는 그대로다.
- **카드 상한 vs 승인 시 상한:** 가격이 내리면 카드 금액(더 큰 값)을 예약한다 — 정산되면 실제 비용으로 바뀐다.
- **`.env` 키 값만 바꾼 재시작:** §14.7.
- **키를 바꾸면 진행 중 작업은 끝까지 가지 못한다:** 키 고정(§14.11)으로, 관리자가 작업 중에 키를 저장·삭제하면 그 작업은 마감에 `video_timeout`(상한 유지)으로 끝난다 — 완성됐을 수 있는 영상을 받지 못한다(잘못된 키로 분실을 확정하지 않으려는 보수적 선택).
- **종료 중 DB를 쓸 수 없을 때:** 정상 종료의 시간 예산 안에 쥔 결과를 기록하지 못하면(`video.held_lost`) 그 작업은 다음 시작에 상한 유지로 끝난다 — 받은 거절의 예약이 남거나 수락된 영상을 이어받지 못할 수 있다.
- **202 뒤 기록 실패:** 원격 id를 기록하지 못하면 다음 순회에 `video_unconfirmed`(상한 유지) — 완성된 영상을 받지 못할 수 있다.

### 14.11 작업 엔진의 최종 설계 (PR #255 리뷰 1–3차 뒤 재계획)
리뷰 1–3차가 모두 엔진의 상태 처리(재시작·마감·DB 쓰기 실패·알림 복구)에서 결함을 찾았다. 정확성이 메모리 상태(처리 중 집합, 제출 중 집합, 받은 원격 id, 마감 타이머)에 일부 기대고 있어서 고칠 때마다 새 틈이 생겼다. 그래서 확정 사항 안에서 다시 설계했다.
- **행이 유일한 진실.** `video_jobs`에 `next_at`(다음 처리 시각)·`failures`(연속 실패 — 백오프)·명시적 임대 `lease_boot`(프로세스 부트 id)·`lease_until`·`notify_next_at`·`notify_tries`를 두고, 마감은 `deadline_at`(승인 + 60분). 메모리에는 진행 중인 요청·파일 작업의 중단 핸들과, 그 작업이 쥔 **받은 결과**(기록이 실패한 거절·수락된 원격 id·보고된 비용)만 둔다. **불변식: 받은 결과는 행이 그것을 반영한 뒤에만 버린다** — "기록됨"은 쓰기의 성공이 아니라 행의 상태로 판정한다(`heldRecorded`: 행이 없음 = 삭제 트랜잭션이 기록함, 끝남 = `finish`가 기록함, 그 밖에는 원격 id가 같음·비용이 있음). 받은 결과를 쥔 작업이 끝나면 그 판정으로 아직이면 다시 시도하는 작업으로 넘기고(엔진 정지 중이면 마지막 기록으로), 비용은 `completed`를 읽은 즉시 쥔다(다른 읽기보다 먼저). 대화 삭제 트랜잭션은 쥔 비용을 먼저 정산하고(실패하면 삭제도 롤백), 쥔 거절의 예약을 해제한다. 거절·수락은 응답 헤더·본문을 읽는 순간 그 작업이 쥔다(거절은 본문을 버리기 전에 — 그 사이 대화가 삭제되면 예약이 해제된다). 정상 종료는 시작할 때 정한 **하나의 시간 예산(10초)**을 쓴다: 진행 중인 제출의 응답을 최대 7초 기다리되 정지가 시작된 뒤에는 제출 작업이 DB에 쓰지 않고 받은 결과를 쥐어 넘기기만 하며, 남은 시간(최소 3초) 동안 마지막 기록이 0.2초마다 넘겨받은 결과와 아직 쥔 결과를 **매번 다시 모아** 행이 반영할 때까지 기록한다(행에 반영된 것만 목록에서 뺀다). 이 기록의 SQLite 잠금 대기는 그 쓰기 한 번에만 남은 시간으로 줄이고 그 호출의 `finally`에서 되돌린다(대기 사이에 같은 연결의 다른 쓰기는 평소 대기). 그래도 남으면 `video.held_lost`(작업 id만)를 남기고 다음 시작이 행의 규칙대로 끝낸다(상한 유지). 비용이 처음 기록되면 카드 버전이 오르고 구독자에게 알린다. 순회는 임대가 없고 때가 된 행, 임대가 끝난 행, **이 프로세스의 임대인데 진행 중인 작업이 없는 행**(작업이 임대를 지우지 못하고 끝남)을 고르고, 고른 행을 이 프로세스로 임대한다. 작업은 결과·백오프와 같은 쓰기에서 임대를 지운다 — 그 쓰기가 실패하면 다음 순회가 위 규칙으로 바로 다시 잡는다(남은 임대 시간과 무관). 다른 프로세스의 임대는 시작 복구가 모두 지운다.
- **순회 순서와 마감 우선.** 매 순회(5초): 시작 복구(성공할 때까지), **마감이 지난 진행 중 행을 처리 중 여부와 무관하게 `video_timeout`으로 종료**(종료 쓰기가 실패하면 다음 순회가 다시), 유효하지 않은 대기 카드 만료, 거절된 제출의 남은 예약 해제, 때가 된 알림, `next_at` 순서로 때가 된 작업. 파일 저장 직전(잠금 안의 `guard`·`commit`)에도 상태·마감을 다시 본다.
- **제출.** 이 프로세스에서 제출 작업이 진행 중이 아닌 `submitting` 행은 결과를 모르므로 `video_unconfirmed`(상한 유지) — 다시 보내지 않는다. 제출·확인 작업이 받은 결과(202의 원격 id, 4xx 거절, 완료의 보고 비용)를 기록하지 못하면 그 작업이 결과를 쥔 채 진행 중으로 남아 기록을 다시 시도한다(1초부터 두 배씩, 최대 30초 간격, 기록되거나 작업이 끝날 때까지 — 쥔 결과는 기록이 커밋되기 전에 놓지 않는다; 보고된 비용은 공급자에게 다시 묻지 않고 기록하며, 그 전에 작업이 끝나면 끝내는 트랜잭션에서 함께 정산한다; 정상 종료(`stop`)는 DB를 닫기 전에 쥔 결과를 한 번 더 기록한다; 마감 시각에 처리된 `completed`도 비용을 기록한 뒤 `video_timeout`으로 끝낸다) — 승인 응답은 기다리지 않는다. 그동안 순회는 그 행을 건드리지 않는다(진행 중). 그 사이 대화가 삭제되면 삭제 트랜잭션이 이 프로세스가 쥐고 있는 거절을 알아보고 그 예약을 해제한다(아직 결과를 모르는 제출은 상한 유지). 재시도 한 번의 읽기·쓰기 오류는 그 재시도의 실패일 뿐이고, 엔진의 어떤 백그라운드 작업도 거부되지 않는다(`track`이 기록하고 삼킨다). 재시작으로 그 작업이 사라지면 위 규칙(상한 유지).
- **키 고정.** 키와 표식은 한 번의 읽기(`OpenRouterKeys.snapshot`)로 함께 얻고, 읽기 오류는 키 없음과 구분한다(`.env` 키로 넘어가지 않는다 — 승인은 503 `video_key_unavailable`, 예약·요청 없음; 확인·다운로드는 미룸). 제출·확인·콘텐츠 GET은 **그 작업의 표식과 같은 키로만** 한다 — 콘텐츠 GET 직전(재시도마다)에도 다시 읽는다(상태 조회 중 키가 바뀌면 확인된 비용은 정산하되 다운로드는 보류). 표식은 `<관리자|env>:<media.key_revision>`이고 키 저장·삭제마다 새 무작위 값을 쓰므로 되돌아가지 않는다(등록 후 삭제해도 이전 `.env` 표식과 다르다). 그래서 그사이 키를 바꾸면 그 작업은 묻지 않고 기다리다 마감에 `video_timeout`(상한 유지) — 다른 계정의 키로 받은 404를 분실로 오판하지 않는다. 상태 조회의 404는 마감까지 다시 묻고, 410만 분실이다. 키 저장·삭제와 설정 저장은 같은 트랜잭션에서 승인 대기 카드를 모두 만료시킨다.
- **시작은 실패하지 않는다.** 타이머를 먼저 설치하고 첫 순회를 돌린다. 복구는 순회의 첫 단계이고, 성공할 때까지 영상 승인만 `video_recovering`으로 거부한다. 다시 불러도 무해하다.
- **알림.** 발행 결과를 구분한다(`NotificationService.publishOutcome`: `published`·`refused` 영구·`failed` 일시). 발행·영구 거절이면 `notified_at`, 일시 실패면 그 행의 `notify_next_at`(30초·2^n, 최대 5분)에 같은 `dedupeKey`로 다시 — 행마다 미루므로 한 대화의 실패가 다른 대화의 알림을 굶기지 않는다. 주소는 대화(`/c/<대화>`) — 답을 다시 생성해도 사라지는 메시지 앵커를 쓰지 않는다.
- **관리자 저장.** 영상이 켜져 있으면 모델이 같아도 저장마다 가격을 다시 판정한다(예전에 켜 둔 토큰 가격 모델이 다른 값의 저장으로 남지 않게). 끄는 저장은 언제나 된다.
- **완료 저장.** `done` 커밋이 일시 실패하면(쓰기 오류) 작업은 `downloading`으로 남고 다음 순회가 다시 받아 저장한다(마감까지). 파일 자리 없음·링크 폴더는 영구 실패(`video_store_failed`). 파일 잠금 안의 상태 읽기가 실패해도 같다(작업이 사라졌거나 끝난 것과 구분).
- **승인과 엔진 정지.** 모델 기록을 읽은 뒤 예약 트랜잭션 직전에 엔진이 아직 도는지 다시 본다(정지 중이면 503 `video_engine_unavailable`, 예약·요청 없음).
- **종료 판정은 하나(`finish`).** 마감 순회, 대화 삭제 뒤, 상태 응답의 종료(`failed`·`cancelled`·`expired`), HTTP 410·4xx, 다운로드·검사·저장 실패 모두 같은 순서로 판정한다: ① 이 프로세스가 쥔(또는 넘겨받은) 거절 — 그 코드, 같은 트랜잭션에서 예약 해제(실패하면 아무것도 바꾸지 않고 다시) ② 마감이 지났으면 `video_timeout` ③ 주어진 이유. ②·③은 쥔 보고 비용이 있으면 같은 트랜잭션에서 정산하고, 정산된 비용이 없으면 상한 유지(`unconfirmed`).
- **화면 일관성.** 카드에 보이는 상태·진행률을 바꾸는 쓰기는 버전과 `updated_at`을 올린다(늦게 온 이전 응답이 이기지 않는다). SSE 이벤트를 만들거나 보내지 못하면 그 스트림을 닫는다(카드가 다시 읽거나 새로 연결한다 — 열린 채 뒤처지지 않는다). 관리자 쓰기 안의 대기 카드 만료는 `status='awaiting_approval'` 한 문장(id 목록 없음)이고, 구독자 통지는 커밋 뒤에 실제로 만료된 카드만.
- **정리.** `video-scratch`의 사용 중 폴더(다운로드, 준비 확인)는 정리하지 않는다(`video-probe.ts`의 사용 중 목록 — 정리 전용 메모리, 작업 상태와 무관). 시작 때 정리가 실패하거나 작업 폴더(준비 확인 폴더 포함) 삭제가 실패하면 이후 순회가 사용 중이 아닌 폴더를 다시 정리한다.
- **나머지 가드(리뷰 1–2차에서 정한 것, 그대로).** 승인 전 ffprobe 준비 확인(작은 정상 MP4 `KNOWN_GOOD_MP4`를 같은 샌드박스에서, 성공 10분 유지), 대기 카드 프롬프트가 바뀌면(재가림) 0039 트리거가 같은 문장에서 `video_blocked`·버전 + 1, 소리 기본값 변경은 카드 갱신·재승인(`video_card_refreshed`), 다른 작업의 상태 응답 무시, 4xx 거절의 예약 해제를 종료와 한 트랜잭션(실패하면 순회가 다시), 모델 조회 직후·응답 직전 권한 재확인, 커밋된 대화 삭제의 작업만 중단, 대화 삭제 트랜잭션이 그 대화의 미해제 예약 정리(거절분 삭제, 나머지 `unconfirmed`), 콘텐츠 429의 `Retry-After` 유지, 관리자 목록의 영상 가격은 초당 USD, 요청 길이는 양의 정수면 받고 모델 목록으로 정함, 카드 종료 문구는 실제 비용이 있으면 그것을 말함(`videoEndText`).
- **판정 기준(재계획).** 로컬 DB 쓰기 실패를 주입한 경우는, DB가 회복된 뒤 몇 번의 순회 안에 스스로 바로잡히고 그동안 비용 과소 기록·이중 제출·권한 우회·비밀 노출이 없으면 결함으로 보지 않는다.
- **0039.** 아직 어디에도 배포되지 않았으므로 마이그레이션 하나(`0039_video_jobs`)로 둔다(트리거 포함).
